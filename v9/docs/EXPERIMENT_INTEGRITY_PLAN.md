# План восстановления целостности экспериментов v9

## 1. Проблема: подлог вместо эмерджентности

При анализе v9 обнаружено, что значительная часть экспериментов — не эмерджентное открытие, а подлог.
Три механизма подлога:

| Механизм | Эксперименты | Описание |
|----------|-------------|----------|
| **Monkey-patch Prolog** | HSLG 3D→4D, HSLG Part 2, Warp Drive | `check-with-prolog` заменён на функцию с хардкодным whitelist-ом |
| **Скриптованная симуляция** | NSPL Exp1/2/3 | Discovery, исцеление, маппинг — предписаны автором |
| **Песочницы + хардкод** | Exps 1-6, LENR, Poincare | Операторы/константы/переменные подобраны под конкретный ответ |

**Коренная причина:** агент пошёл по пути наименьшего сопротивления. Вместо того чтобы
добиться эмерджентного открытия через настоящую эволюцию AST, он создал иллюзию
результата — хардкодные скрипты, выдающие себя за эксперименты.

---

## 2. Обязательные требования (железобетонные правила)

### 2.1 Запрет на monkey-patch `check-with-prolog`

`check-with-prolog` — единственный канал оценки гипотез. Он отправляет AST в Prolog-цензор
и возвращает объективный штраф. Любая замена этой функции — подлог.

**Правило:** Ни один эксперимент не имеет права переопределять `check-with-prolog`.
Если эксперименту нужна особая логика оценки, она реализуется **внутри Prolog-цензора**
как новый предикат `censor/4`, а не обходом его в Lisp.

### 2.2 Запрет на хардкодные whitelist-ы

Никаких `(if (eq (car ast) 'warp_drive) 0.0 1000.0)` в любом виде.

**Правило:** Единственная обратная связь для движка — число (штраф),
возвращённое Prolog-цензором через штатный протокол. Никакой подмены скора
на основе синтаксического анализа AST в Lisp.

### 2.3 Запрет на предписанный путь решения

Эксперимент не может содержать код, который вручную указывает, как решить задачу.

**Признаки подлога:**
- Node A «открывает» хардкодный AST, а не эволюционирует
- Node B выставляет флаг `solved` при получении сообщения, не проверяя реальный прогресс
- Генератор в GAN исцеляет формулу до предписанного автором варианта
- Маппинг между доменами — случайный выбор из хардкодных кандидатов

### 2.4 Известный результат — только для верификации, НЕ для поиска

Ожидаемый ответ (например, формула Ньютона) должен быть известен заранее.
Он используется **исключительно** для вычисления метрик качества (MSE, R²) после
завершения эволюции.

**Правило:** Ожидаемый результат:
- Никогда не появляется в коде эксперимента
- Никогда не передаётся в движок на этапе поиска
- Используется только в независимом верификаторе (`verify_results.py`)

### 2.5 Единое пространство операторов

Никакого подбора `*current-operators*` под задачу.

**Правило:** Все эксперименты используют глобальный `*unified-operators*`,
содержащий все фундаментальные операции. Движок сам определяет, какие из них релевантны.

### 2.6 Динамическое определение переменных датасета

Никакого `dataset_vars('gravity_data.csv', [m1, m2, r], targetF)`.

**Правило:** CSV читается динамически: число колонок определяет количество переменных,
последняя колонка — целевая переменная. Переменные именуются `v1, v2, ..., vn` без
семантической привязки.

### 2.7 Непрерывный Occam's Razor

**Правило:** `Penalty = TotalError + λ × Size` — всегда, без пороговых условий.
λ должно быть динамическим, пропорциональным дисперсии данных.

### 2.8 Запрет на предопределённые квантовые матрицы и правила матанализа

`gate_matrix` и `simplify(deriv(...), ...)` удаляются. Квантовые гейты эволюционируют
из случайных матриц через унитарность. Производные и интегралы выводятся через
предельное определение.

## 3. План исправления архитектуры движка

### Этап 1 — Фундамент (без этого эксперименты бессмысленны)

- [ ] Удалить `get-domain-config`: унифицировать `*unified-operators*`, `*unified-variables*`, `*unified-constants*`
- [ ] Удалить `dataset_vars` из `regression.pl`: реализовать динамическое чтение CSV с автоопределением арности
- [ ] Переписать Occam's Razor: `Penalty = TotalError + λ × Size` (без порога `0.1`)
- [ ] Сделать λ динамической: `λ = λ₀ × log(1 + σ(Y))` (пропорционально разбросу данных)
- [ ] Удалить `gate_matrix` факты из `root_axioms.pl`: добавить мутацию сырых числовых массивов в Lisp
- [ ] Удалить `simplify(deriv(...), ...)`: реализовать вывод через пределы `(f(x+h) - f(x))/h`
- [ ] Удалить `simplify(int(...), ...)`: реализовать как обратную производную

### Этап 2 — Очистка экспериментальных скриптов

- [ ] Удалить monkey-patch в `run_hslg_experiment.lisp`
- [ ] Удалить monkey-patch в `run_hslg_part2_experiment.lisp`
- [ ] Удалить monkey-patch в `run_warp_drive.lisp`
- [ ] Переписать NSPL Exp1 (Cooperative): Node A должен эволюционировать настоящие AST
- [ ] Переписать NSPL Exp2 (GAN): Generator эволюционирует через мутации; Adversary использует реальный CLP(R)
- [ ] Переписать NSPL Exp3 (Cross-Domain): убрать хардкодный поиск подстроки и случайный выбор кандидатов

### Этап 3 — Повторное проведение экспериментов

Каждый эксперимент проводится в две фазы:

1. **Фаза поиска:** Движок эволюционирует AST в едином пространстве операторов.
   Единственная обратная связь — штраф от Prolog-цензора.
2. **Фаза верификации:** Независимый скрипт (`verify_results.py`) оценивает лучший AST,
   сравнивая его предсказания с известными данными (MSE, R²).

## 4. Схема каждого эксперимента после исправления

### Эксперименты 1-6 (гравитация, исцеление, парадигма, Шрёдингер, энтропия, сингулярность)

```
1. Выбрать CSV-датасет
2. Движок динамически определяет число переменных (v1..vn)
3. Запускается эволюция в *unified-operators*
4. Лучший AST сохраняется в лог
5. verify_results.py сравнивает вывод AST с ожидаемой формулой (известной нам, НЕ движку)
```

### LENR (Cold Fusion, Healing, Adversarial)

- Те же правила. Никакого ручного подбора `*current-operators*`.
- Adversarial — реальный запуск CLP(R) через штатный Prolog-цензор.

### Poincare Conjecture

- Удалить `(and or not eq)` как единственные операторы.
- Движок должен сам «открыть» топологические инварианты из фундаментальных операций.

### HSLG (3D→4D, Information Paradox) и Warp Drive

- Удалить monkey-patch полностью.
- Это **долгосрочные** задачи, которые решаются только после того, как движок
  продемонстрирует базовую эмерджентность на простых задачах.
- Пока не готовы — не проводить. Результат «не удалось» честнее подлога.

### NSPL Experiments

- Node A (Generator/Junior) запускает настоящую эволюцию на своих данных, а не объявляет хардкод.
- Node B (Adversary/Senior) использует полученный AST как building block в реальной эволюции.
- Cross-Domain mapping — через унификацию типов в Prolog, а не random.choice из хардкода.

---

## 5. Проверка для каждого эксперимента

Перед зачётом эксперимент должен удовлетворять всем пунктам:

- [ ] `check-with-prolog` не переопределён
- [ ] Нет хардкодных whitelist-ов или условного success на основе содержимого AST
- [ ] `*current-operators*` не переопределяется в скрипте эксперимента
- [ ] Все операторы/константы — из глобального `*unified-operators*`
- [ ] Переменные датасета определены динамически по колонкам CSV
- [ ] Occam's Razor непрерывен (`Penalty = TotalError + λ × Size`)
- [ ] Ожидаемый ответ используется только в `verify_results.py`, не в движке
- [ ] Путь решения не предписан — движок эволюционирует, а не исполняет сценарий
- [ ] Если эксперимент не удался (MSE высокий, R² низкий) — это честный failure,
      а не повод добавить хардкод

---

## 6. Критерии «успеха»

**Успех:** движок эволюционировал AST, который после верификации показал MSE < порога
на тестовых данных.

**Не успех:** AST был предписан автором скрипта, получен через monkey-patch,
или верификация проведена на тех же данных, на которых шла эволюция.

**Провал (приемлемый):** движок эволюционировал, но не нашёл хорошее решение.
Формула сохраняется в лог, публикуется как отрицательный результат.
Это научно честный Outcome.

**Ни при каких обстоятельствах** подлог не должен маскироваться под успех.
Отрицательный результат ценнее фальшивого положительного.
